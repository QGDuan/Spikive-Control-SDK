# Spikive Control SDK：接口评审与开发

SDK 负责命令转发、状态监视和接口整理。用户要求的范围决定本轮是文档评审还是代码开发；评审和“可实现”分类不构成功能实现授权。

## 先确认事实

- 定位实际 SDK 仓库、用户指定 PDF、后端版本和 launch；记录 Git 提交，非 Git 源码记录关键文件校验值。不要把另一个 SLAM 分支或旧实验的能力混入本次结论。
- 以 SDK 仓库根目录读取 README、`docs/开发逻辑.md`、`docs/README_坐标对齐与验证.md` 及本轮评审文件。这些路径相对仓库，不相对 Skill 安装目录。
- 沿消息定义→发布者→订阅者→状态回报核对。Planner 内部变量、日志、注释掉的代码、启动参数不自动等于可订阅接口或运行时配置入口。
- PDF 是客户要求，源码是当前能力。新 PDF 的字段增删、类型或枚举含义变化必须显式对照；不能把消息改名或同编号枚举当成协议兼容。用户没有要求迁移时，不修改运行消息定义。

## 文档评审与三类维护

- 保留原文第 3 章的编号、接口名称和定义；代码块只修复 PDF 排版换行，不悄悄修改字段、注释或枚举。每个接口只补一张表：`编号 | 字段或能力 | 分类 | 现有来源及处理 | 当前是否实现`。
- 按字段或独立能力拆行。使用稳定编号，例如 `3.1.2-yaw`；阶段中能确认与不能确认的部分分开，不能整接口笼统归类。
- 三类固定为：**可实现**、**值得实现＋后续实现**、**无必要实现／保持现有状态**。未决定项用“待归类”暂存，不算第四类。
- 初次整理仅填写有源码依据、可由现有接口复用、话题映射或轻量 SDK 转换完成的“可实现”。当前状态分别写“已实现”“部分实现”“尚未实现”，并限定该行含义；可实现不代表值得开发、已经上线或整个协议可用。
- 第二、第三类初次只留标题，由用户后续指定。证据不足的项目写清事实缺口，留待归类；不代用户作价值判断。
- 用户按编号给出分类或要求时，只更新相关行和文首汇总，保留原定义及证据。分类不是实现状态：移入后续实现不能改成“已实现”。拆行后保留旧编号的去向说明，不复用旧编号表示另一能力。
- “待确定＋后续实现”归入第二类，同时保留“是否实施待确定”和复杂度，不视为确定开发承诺。同名状态按接口编号分别处理，不把 Goto 的决定自动扩展到全局 FlightState。
- 明确区分：仅配置/relay 即可、已有 SDK 转换、需要新增 SDK 处理、后端缺少支持。表内用短句，较长的共性坐标解释放一张表或一张流程图，不重复铺陈。
- 证据指向当前文件/函数或固定提交。发布到独立仓库的文档不使用只在作者机器存在的临时文件链接；工作区外依赖写明源码相对位置或固定提交链接。

## 坐标与话题映射

- 保留 SLAM/Planner/WayPoint 的源码和坐标约定；除非用户明确扩大范围，不通过修改后端满足外部接口。不重新定义原点、换轴、加负号或绕过既有控制器发 setpoint。
- 仅话题映射使用已有 remap/relay/配置，保留消息类型、字段、Header、数值与采样时间。重命名话题不改变 frame；修改 frame 字符串不构成坐标变换，也不能把低频缓存变成高频观测。
- 说明每个位置/姿态的原点、轴向、单位、参考 frame、时间以及变换方向。未知的地理东/北、body 与 base_link 外参或飞控本地原点对齐，明确保留未知，不根据名称猜测。
- 当前项目地图、初值及导航目标使用原生 world。Goto 距离和到达时长读取 Planner 同源 `/drone_{id}_visual_slam/odom`，检查 frame、非零时间戳和有限 xyz；不回退到 MAVROS 位置。MAVROS 仍用于起飞相对高度、速度模长、连接及起降状态。
- fusion_repub 初始化前后都可能标 world，数值分别来自启动坐标与对齐后的地图坐标。diff_odom 是修正变换，不是机体位姿；不能再次修正已对齐的导航输出。source twist/协方差未填时，默认零不是有效速度或零误差。
- 起飞前只执行一次地图匹配任务。`continuous_match=false` 成功后停止地图 ICP；连续成功确认属于该初始化任务内部。LIO 后续仍更新位姿，fusion_repub 应用固定修正。SDK 不自动重复发初值。

## 命令、状态和能力边界

- 优先已有控制器/Planner 对外状态，缺失信息再补 MAVROS；必要的距离、模长、时间单位转换写明公式。没有发布的 FSM 枚举不能声称直接可取；重规划不等于 AVOIDING，低速不等于已确认 HOLDING。
- 区分“已转发”“控制器已完成”“已上锁”。发布者/订阅者存在不代表收到命令 ACK；时间戳晚于命令仅排除旧缓存，不证明请求严格对应，也不证明数据新鲜。
- Takeoff：cmd=1；成功用新的 tookoff 且连接有效。目标高度、速度、timeout 当前预留；实际由后端决定，不增加虚构 STABILIZING。
- Land：cmd=2；新 landed 加新 MAVROS ON_GROUND 确认着地，连接有效；disarmed 单独依据新的 State.connected 且 !armed。LANDING 不能当触地检测，height 使用有效 bottom_clearance，不混用坐标 z 或前方地形高度。
- 用户同意 GROUND_DETECT 复用 ON_GROUND 时，说明它是已着地确认，不是独立提前触地信号；与 TOUCHDOWN 可共用证据。当前读取 ON_GROUND 不等于已经输出 phase=2。
- Goto：Continue cmd=4→0.2 s→原生 GoalSet，延迟不是 ACK；新 reached 配合同源里程计距离及稳定时长。GoalSet 没有逐次速度/yaw 输入，PositionCommand 有 yaw 不代表客户可直接指定目标航向。
- Return：cmd=3；返航点归 FlightManager，不自动取 SDK 起飞点或重定位初值。false→true 的 returned 仍不是目标 ACK；不自动降落。连续 cmd=3 也不保证重新派发。
- 四个飞行 Action 共用本节点任务槽，不约束外部发布者。取消仅结束跟踪；Goto 取消可撤销未触发的定时发送，不撤回已发命令，不额外悬停/停桨/降落。
- 急停、悬停与恢复必须核对现有命令行为和生效分支；保持历史位置不是停桨，Continue 发送当前位置不是恢复旧航线。语义未定时不伪造成功能力。
- LoadMap 成功只表示地图得到确认；Relocalize 成功来自本轮开始证据、后端 localized 和有效新修正。不得用舍入后的 fitness 再否定后端成功；状态/变换缺少共同请求 ID 的限制如实记录。
- bag 录制、PCD 采集、项目保存、后处理分别核对；文件生成不代表后处理完成。点云限频/降采样属于处理支路，不是仅话题改名，不修改规划或定位输入。

## 实现、校验与交付

- 代码开发保持轻量 Config、消息封装和一个 SDK 节点。不要新增控制算法、MAVROS 上锁/解锁/模式调用或内部控制服务来弥补后端缺口。按实际任务保留已有公开接口。
- 核对按 drone_id 生成的话题与部署一致，特别是 SDK 默认 1、既有 Orin 后端曾使用 2；不把历史编号当所有环境的默认值。
- 当前普通 Action/状态回调单线程，LoadMap 有独立服务队列与锁；新增共享状态先核对线程归属和互斥。
- 文档变更检查原文字段覆盖、稳定编号唯一、分类/数量一致、链接有效、依据可追溯和运行文件未变；不为纯文档变更虚报新编译或飞行验证。
- 修改 C++ 或消息后，在已有 Noetic/MAVROS Docker 临时工作区构建本包及消息依赖，做针对性离线验证；不向现有 ROS master 发送飞行测试命令。编译通过不代表实机验证。
- 修改 Skill 后运行 skill-creator 的 quick_validate.py，并检查规则是否符合用户当前决定。仓库 `skills/spikive-control-sdk/` 与本机安装副本保持同步，保留无关 UI/权限元数据。
- 推送以用户授权的仓库和分支为准；先查看差异，不提交临时构建产物。报告真实提交和验证边界，不把文档里的未来接口说成已经上线。
