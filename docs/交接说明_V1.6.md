# v1.6 同事交接入口

## 获取与构建

线上仓库：<https://github.com/QGDuan/Spikive-Control-SDK>。先阅读 [开发记录](开发记录_V1.6.md) 和 [地面站交互协议](地面站交互_V1.6.md)。main 后续可能继续变化；部署时记录 `git rev-parse HEAD`。

本仓库是 ROS 包源码，不是完整工作区。运行环境：ROS1 Noetic、C++14、MAVROS、rosbag、PCL、OpenSSL、Boost；另外需要现有工程的 controller_msgs、quadrotor_msgs 原版消息包。

在已有消息依赖的工作区中克隆（已有 SDK 时先检查本地修改，避免重复包）：

```bash
cd ~/sdk_ws/src
git clone git@github.com:QGDuan/Spikive-Control-SDK.git
cd ~/sdk_ws
source /opt/ros/noetic/setup.bash
catkin_make --only-pkg-with-deps spikive_control_sdk -j2 -l2
source devel/setup.bash
rosversion spikive_control_sdk
rosmsg show spikive_control_sdk/RecordGoal
rosmsg show spikive_control_sdk/PostProcessGoal
```

版本应为 1.6.0，RecordGoal 应包含 topics。Record 消息 MD5 已改变，客户端和桥接端使用的消息定义需要一起更新。PostProcess 为新增 Action，客户端需使用本仓库生成的消息定义。源码 ZIP 直接放入已有工作区 src；其中 packaging/install.sh 是完整安装包的辅助脚本，不适用于单包源码 ZIP 根目录。

原系统负责启动 SLAM/Planner/MAVROS。退出旧 SDK 节点后：

```bash
roslaunch spikive_control_sdk spikive_control_sdk.launch drone_id:=2
```

仅录包可用 `roslaunch spikive_control_sdk map_record.launch`；仅点云后处理可用 `roslaunch spikive_control_sdk post_process.launch drone_id:=2`。各终端先 source 新工作区；不要同时启动新旧同名 SDK 节点。默认 drone_id=1，现场示例使用 2，按实际设备配置。

## 接手验收

1. 核对 ROS master、SDK 版本、drone_id、话题发布订阅及原生 world 坐标；不要通过改 frame 字符串掩盖坐标不一致。
2. 按 [命令行测试](README_命令行测试.md) 做接口联调。先订阅 feedback/result，再发唯一 goal_id。飞行验证需在现场已准备好的测试条件下执行。
3. 录包先用两三个确实有数据的话题验证开始→停止→rosbag info，再使用现场完整话题列表，检查实际消息数和负载。
4. LoadMap 在 SDK 所在机器/容器内使用真实 PCD 绝对路径；加载成功后另发 Relocalize 初值。成功只做一次初始化匹配，后续 LIO 继续更新。
5. 前端核对拒绝、取消、超时、断线重连，不把发布成功或 ACTIVE 当作飞行/定位完成。

隔离测试命令（不要连接实机 master）：

```bash
catkin_make run_tests_spikive_control_sdk -j2 -l2
catkin_test_results build/test_results
```

未完成事项和已知限制见 [开发记录](开发记录_V1.6.md)。交接不包含已确认解决现场 yaw 问题的承诺。
